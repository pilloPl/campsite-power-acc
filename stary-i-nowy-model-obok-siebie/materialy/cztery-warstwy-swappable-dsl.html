Cztery warstwy na jednym scenariuszu

Jeden scenariusz z przebiegu workflow i droga, którą przechodzi przez cztery warstwy: raz do starego systemu, raz do nowego modelu Party. Kod jest z przebiegu, skrócony.

1Scenariusz: co

Czyta się jak zdanie biznesowe: given świat, potem pytanie i dzisiejsza odpowiedź. Nie ma w nim ani słowa o grupach, drzewie, bazie czy Party. Scenariusz nie wie, kto mu odpowiada.

@Test
default void card_of_issuer_with_agreement_works_at_pedestal_of_that_campsite() {
    // given
    dsl().campsite("BAY");
    dsl().pedestal("BAY-P001", "BAY");
    dsl().issuer("CARAVAN CLUB");
    dsl().agreementWithCampsite("CARAVAN CLUB", "BAY");
    dsl().guestCard("2001", "CARAVAN CLUB");
    //then
    assertThat(dsl().isCardAcceptedAt("2001", "BAY-P001")).isTrue();
}

2DSL: słownik

Słowa, którymi pisze się scenariusze: komendy świata (kemping, słupek, wydawca, umowa, karta gościa) i pytania portu. Sam interfejs, bez logiki. Słowa mechanizmu starego systemu są tu zakazane, a pilnuje tego grep słownika zakazanego.

interface AcceptanceDsl extends AcceptanceWorld {   // komendy świata: campsite, pedestal, issuer, agreementWithCampsite, guestCard…
    boolean isCardAcceptedAt(String uid, String pedestal);
    Set<String> issuersAcceptedAt(String pedestal);
    boolean isNetworkCard(String uid);
}

3Sterownik: jak, osobno dla każdego modelu

Tłumaczy słowa DSL na konkretny system. Ten sam scenariusz dostaje różne sterowniki, a cała wiedza o mechanizmie siedzi tylko tutaj.

Stary system

„Kemping” to grupa w drzewie, zakładana tym samym serwisem co w konsoli. Umowa to dopięcie grupy kempingu do listy wydawcy. Słupek i karta idą przez DAO, do prawdziwej bazy testowej. Przed pytaniem flush i clear, żeby stary kod czytał z bazy, jak w żądaniu. Pytanie robi te same wywołania co dziś ValidationService.

public void campsite(String name) {
    places.put(name, groupManager.createChildGroup(
        groupService.fetchSiteGroup(MARKET_SITES), name, name).getId());
}
public void agreementWithCampsite(String issuer, String campsite) {
    groupManager.addAcceptanceAgreement(issuerGroup(issuer), placeGroup(campsite));
}
public boolean isCardAcceptedAt(String uid, String pedestal) {
    entityManager.flush(); entityManager.clear();
    return acceptance.isCardAcceptedAt(CardRfid.of(uid), PedestalCode.of(pedestal));
}

Nowy model Party

„Kemping” to podmiot (jednostka organizacyjna). Umowa to relacja między wydawcą a kempingiem. Słupek to tylko rzut „stoi na kempingu K”. Wszystko w pamięci, bez bazy i bez Springa; prawo do prądu model wyprowadza z relacji.

public void campsite(String name) {
    places.put(name, party.parties()
        .registerOrganizationUnit(name, Role.ACCEPTOR).id());
}
public void agreementWithCampsite(String issuer, String campsite) {
    party.relationships().assign(issuerId(issuer), placeId(campsite),
        RelationshipName.ACCEPTANCE_AGREEMENT);
}
public void pedestal(String code, String campsite) {
    party.pedestals().standsAt(code, placeId(campsite));
}

4System pod testem

Tu siedzi to, co odpowiada: stary kod na prawdziwej bazie albo nowy moduł. Sterownik wybiera klasa testu, raz. Scenariusze są te same, napisane raz.

class LegacyAcceptanceScenariosTest extends IntegrationTest implements AcceptanceScenarios {
    // sterownik: AcceptanceLegacyDriver(LegacyAcceptanceWorld, LegacyCardAcceptance, entityManager)
}

class PartyAcceptanceScenariosTest implements AcceptanceScenarios {
    // sterownik: AcceptancePartyDriver(PartyAcceptanceWorld, PartyCardAcceptance) — świeży model na scenariusz
}

Po co ten podział

  • Zielone scenariusze na obu sterownikach znaczą, że oba modele odpowiadają w tych miejscach tak samo.
  • Gdy zmienia się stary mechanizm, poprawiasz tylko sterownik, testy zostają bez zmian.
  • Słowa starego systemu są tylko w sterowniku legacy; scenariusze i DSL mówią językiem pytań.
  • Seeder zasila oba modele tymi samymi komendami świata, więc w działającej aplikacji pytania na ekranie trafiają w te same dane.
