Upgrade Spring Boot w campsite-power-acc — analiza z dowodami

Repo: pilloPl/campsite-power-acc, master, commit 938d4ab53e242d72c3f48bccb5be6196cccaeaf8.

Wniosek: przejście z Boota 3.5.7 do 4.1.2 obejmuje backend, infrastrukturę testów i kontrakt OpenAPI konsumowany przez frontend. Samo przestawienie numeru wersji nie przechodzi nawet mvn validate. Nie znalazłem wymuszenia podbicia Javy 21, PostgreSQL 16 ani Reacta 18. Największy koszt to zachowanie semantyki JSON, autokonfiguracji, transakcji i integracji HTTP.

To analiza gotowości i zasięgu zmiany. Oryginalne repo pozostało bez zmian. Eksperymenty dotyczą POM-ów w osobnych kopiach; nie stanowią ukończonej migracji. Nie uruchomiono kompilacji, testów aplikacji ani serwera — dostępne środowisko ma JRE 17, bez JDK 21 i Dockera. Udane rozwiązywanie zależności nie dowodzi zgodności binarnej ani poprawnego zachowania.

1. Jak daleko sięga drzewo

Policzyłem wynik dependency:tree -Dverbose dla wdrażanego modułu campsite-server, obejmujący także zależności testowe. Wiersze odrzucone przez Maven jako duplikaty/konflikty pomijam. To unikalne współrzędne groupId:artifactId:type[:classifier], bez wewnętrznych io.pillopl; nie liczba plików faktycznie spakowanych w JAR.

3. „Z tym będziesz się szarpać” — konkretne znaleziska

A. Pierwsza blokada jest przed kompilacją

W kopii repo zmieniłem wyłącznie parent 3.5.7 → 4.1.2 i uruchomiłem mvn validate. Wynik:

'dependencies.dependency.version' for org.testcontainers:junit-jupiter:jar is missing.
'dependencies.dependency.version' for org.testcontainers:postgresql:jar is missing.
The build could not read 3 projects

Każdy z błędów występuje w core, endpoints i server: łącznie sześć. Przyczyna: BOM nowej linii zarządza przemianowanymi artefaktami. Dowody w repo: core, endpoints, server; wydanie Testcontainers 2.

Zamiana na testcontainers-junit-jupiter i testcontainers-postgresql wystarczyła, aby validate oraz effective-pom przeszły. Nie wystarcza do ukończenia migracji.

Wspólna konfiguracja używa org.testcontainers.containers.PostgreSQLContainer<?>: plik. Inspekcja JAR-a 2.0.5 potwierdziła zarówno nową klasę org.testcontainers.postgresql.PostgreSQLContainer, jak i klasę w starym pakiecie. Nie zgłaszam więc nieistniejącego dowodu „stary import na pewno się nie skompiluje”. Docelowo należy przejść na nowe API, sprawdzając także deklarację typu i konstruktor. Fixture jest eksportowane jako test-JAR: konfiguracja, więc jego zmiana propaguje się dalej.

B. Jackson: nie tylko importy

Bezpośrednie importy Jacksona 2 występują w 2 plikach produkcyjnych i 5 testowych. Najważniejsze:

  • ConsoleAuthenticationEntryPoint: wstrzykuje com.fasterxml.jackson.databind.ObjectMapper i serializuje błędy security.
  • PedestalCommunicationLogListener: serializuje atrybuty zdarzenia do danych zapisywanych w bazie; przechwytuje JsonProcessingException.
  • test listenera: ręcznie konstruuje mapper i rejestruje JavaTimeModule.
  • baza testów HTTP: wspólny mapper wpływa na całą rodzinę testów.

Boot 4 domyślnie konfiguruje Jacksona 3 i JsonMapper; API databind/core przechodzi do tools.jackson. Potrzebna jest adaptacja konstrukcji mappera i obsługi wyjątków, a nie globalny replace wszystkich pakietów. Adnotacje Jacksona mają odrębne zasady. Dokumentacja JSON Boot 4.1.

Ryzyko semantyczne: daty, enumy, null/missing, liczby, nazwy pól oraz błędy dekodowania mogą zmienić kontrakt nawet przy zielonej kompilacji. Testować payloady wejściowe ze słupków i wyjściowe z konsoli oraz JSON zapisany w logu komunikacji. Sam test z nowym mapperem po obu stronach może zamaskować regresję — potrzebne są utrwalone przykłady z wersji obecnej.

Dokumentacja 4.1 nadal opisuje przejściowy moduł spring-boot-jackson2. To możliwy sposób etapowania, lecz oznacza utrzymywanie dwóch stosów i jawny wybór konwerterów. Model docelowy w tym raporcie zakłada Jacksona 3; nie dodano mostka.

C. Flyway i RestClient: aplikacja może stracić konfigurację bez oczywistego błędu kompilatora

Core POM deklaruje spring-web, flyway-core i moduł PostgreSQL, a application.yml wymaga migracji przed walidacją schematu. W nowym układzie modułów należy zapewnić spring-boot-starter-flyway i zachować flyway-database-postgresql.

Trzy klienty stosują ObjectProvider<RestClient.Builder>.getIfAvailable(RestClient::builder): V1, V2, IssuerExchangeV2. Brak beana nie musi zatrzymać startu: kod tworzy własny builder. To miejsce, gdzie można po cichu utracić konwertery i customizery. Zapewnić starter restclient oraz test obecności i konfiguracji beana. Timeouty i SimpleClientHttpRequestFactory są ustawiane jawnie w tych klasach; należy zachować ich działanie.

Dowód platformowy: Boot 4 migration guide; inspekcja spring-boot-restclient-4.1.2.jar pokazała RestClientAutoConfiguration w tym module. Nie zaobserwowano rzeczywistego startu z brakującym beanem — jest to ryzyko wynikające z kodu i podziału modułów.

D. Testy MockMvc zmieniają moduł i pakiet

WebServiceIntegrationTest:7 importuje starą AutoConfigureMockMvc. W JAR-ze 4.1.2 potwierdziłem nową klasę:

org/springframework/boot/webmvc/test/autoconfigure/AutoConfigureMockMvc.class

Wariant docelowy zapewnia spring-boot-starter-webmvc-test. Zmiana wspólnej klasy testowej ma duży zasięg. Starter security-test porządkuje integrację testów security; nie twierdzę, że każde obecne wywołanie SecurityMockMvcRequestPostProcessors wymaga go zamiast samego spring-security-test. Repo już używa @MockitoBean; nie znaleziono potrzeby hurtowej migracji @MockBean.

E. OpenAPI może uszkodzić TypeScript bez zmiany Reacta

client.ts:19 zakłada odpowiedź 200 z content['*/*']; request oczekuje application/json. Jeśli nowy springdoc opisze odpowiedź bardziej precyzyjnie jako application/json, typ ResponseOf może spaść do unknown. To hipoteza do sprawdzenia diffem schematu, a nie zaobserwowany wynik nowego serwera.

Sprawdzić /v3/api-docs, uruchomić npm run generate-api, obejrzeć diff schema.d.ts, następnie npm run typecheck i testy klienta. Skrypty. Ważny szczegół: Dockerfile:7 wykonuje samo npx vite build, więc budowa obrazu nie zastępuje osobnego sprawdzenia typów.

5. Kontrakty i rzeczywiste użycie

ConsoleSecurityConfiguration definiuje trzy różne ścieżki: konsola z sesją i CSRF, aplikacja QR z Basic Auth oraz otwarty pedestal-link identyfikujący urządzenie kodem. Zachować nazwy XSRF-TOKEN, X-XSRF-TOKEN, CORS z credentials, cookies i zakresy wyłączenia CSRF. Konfiguracja już używa lambda DSL. Security 7 zmienia domyślne dopasowywanie ścieżek; obecne wzorce wyglądają prosto, ale wymagają testów dostępu. Dokumentacja migracji matcherów.

Istniejący ConsoleLoginHttpIntegrationTest używa java.net.http.HttpClient i CookieManager, nie TestRestTemplate. Nie przypisuję mu więc mechanicznie zmian cookie handling z release notes TestRestTemplate.

Klienty V1/V2 i IssuerExchangeV2 są granicami protokołu: adresy, request/response DTO, timeouty i mapowanie błędów należy porównać na przykładach obu stron. Zmiana bibliotek nie dowodzi konieczności aktualizacji firmware ani systemu partnera.

Co faktycznie jest używane produkcyjnie: nieustalone. Analiza objęła źródła, konfigurację i testy; nie otrzymałem logów produkcyjnych, traces, metryk ruchu ani parametrów rzeczywistego wdrożenia. W POM-ach i konfiguracji nie znalazłem jawnego eksportera tracingu. Obecność micrometer-observation tranzytywnie nie jest dowodem, że ktoś zbiera traces.

Są punkty, z których można pozyskać dowód użycia:

  • EventListener:111: logi obciążenia executorów i błędów obsługi.
  • PedestalCommunicationLogListener:69: warunkowo zapisywane komunikaty urządzeń. Brak wpisu może wynikać z konfiguracji logowania, a nie braku użycia.
  • QrPayProcessSupervisor:136: przebiegi operacji QR.

Do priorytetyzacji potrzebne są częstotliwości endpointów/wersji protokołu, aktywne joby, rozkłady opóźnień, błędy i wywołania integracji z reprezentatywnego okresu. Bez nich nie oznaczam żadnej funkcji jako martwej ani nieważnej.

7. Minimalny zakres prac i kolejność

  1. Utrwalić punkt odniesienia na 3.5.7. Build na JDK 21, istniejące testy, przykładowe odpowiedzi JSON i OpenAPI, wyniki najważniejszych operacji SQL oraz cookies. Zweryfikować istniejącą bazę na kopii.
  2. Przejść na najnowsze 3.5.x, obecnie 3.5.16. Osobno sprawdzić regresje i deprecacje. To zalecany punkt przygotowania do Boot 4, nie warunek narzucony przez Maven.
  3. Przygotować spójny zestaw dla Boot 4. Wariant eksperymentalny 4.1.2 zawiera zmiany z poniższej tabeli; kod nadal wymaga adaptacji Jacksona i testów. Opcjonalny checkpoint 4.0.9 musi mieć własną zgodną wersję springdoc i osobną walidację; nie zakładać, że przejście 4.0 → 4.1 jest puste.
  4. Sprawdzić start i dane. Flyway na pustej i istniejącej bazie, schema validation, beany klientów, auth, działanie jobów; następnie regresja z sekcji 4.
  5. Sprawdzić granice systemu. OpenAPI diff, generacja i typecheck TS, scenariusze sesji/CSRF, odtworzenie komunikatów V1/V2 i QR. Utrwalić wyniki, nie tylko zielony build.
  6. Próba wdrożenia i powrotu. Sprawdzić start w limitach pamięci z Dockerfile, kończenie requestów i executorów. Powrót do starego obrazu jest bezpieczny tylko przy potwierdzonej zgodności schematu i zapisanych danych; samo zachowanie obrazu nie wystarcza.
